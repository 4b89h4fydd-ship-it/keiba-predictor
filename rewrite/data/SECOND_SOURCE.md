# 第2取得経路の設計（slice系統から取り込んだ設計）

状態: **設計のみ。稼働は権利確認後**（下記ゲート参照）。

主軸の取得は本番API（利用者自身のサービス）経由が正。本経路は、
単独依存を下げるための第2経路として、並行実装だった slice 系統の
`rewrite/slice/acquire.py` の設計を精査のうえ取り込んだもの。
slice のパーサー自体は対象2レース専用（タイトル・日付が固定）に
作られており取り込まない。一般化した取得層だけをここに定義する。

## 取り込んだ設計（slice acquire.py の実物を確認済み）
- ホスト許可リスト方式: 許可したホスト以外は取得しない
- robots.txt を必ず読み、`can_fetch` と crawl-delay を尊重する
- 取得した原バイトはそのまま保存し、SHA-256 で検証する。
  キャッシュは URL ハッシュをキーにし、再読時にハッシュ不一致なら例外
- 文字コードはページ宣言から判定する（Shift_JIS 系は cp932）
- HTTP エラー時も原バイトを残し、失敗として記録する（握りつぶさない）
- 取得元・取得時刻・バイト数・ハッシュをメタデータとして必ず残す

## 追加で得られるもの
- Yahoo 出馬表は馬の恒常ID（horse_id）を持つ。本番API経由では
  得られない「レースをまたいだ馬の同一性」が確保でき、
  過去走の名寄せ精度が上がる。第2経路の正規化では horse_id を
  馬の識別子として保持する

## 稼働ゲート（すべて満たすまで定期実行しない）
1. 各ソースの商用利用可否を利用者と確認済みであること
   （slice 側の調査でも未確認のまま。未確認では設計止まり）
2. robots が禁止する対象（NAR公式の動的出馬表など）は恒久的に対象外
3. 取得間隔は robots の crawl-delay 以上。大量取得の前に対象件数を申告する

## 付記: MotherDuck 照合への流用

総当たりで探す手法）は、MotherDuck スナップショットのハッシュ不一致
（417件中5件）の照合にそのまま使える。アクセス権が得られた時点で
この手法で照合し、書き換えは一切しない。
